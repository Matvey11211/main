## Ответы на вопросы

### 1. Что такое идемпотентность и почему она важна?

Идемпотентность — это свойство операции, при котором многократное её выполнение даёт тот же результат, что и однократное. В Ansible это означает, что playbook можно запускать повторно без побочных эффектов: если nginx уже установлен и настроен правильно, Ansible не будет его переустанавливать. Это критически важно для надёжности автоматизации — администратор может безопасно применять конфигурации, не боясь нарушить работу системы или вызвать простой сервиса.

### 2. Зачем нужен `notify` и `handlers`? Почему не просто `restart` в tasks?

`notify` и `handlers` реализуют паттерн "уведомление-действие": задача отправляет уведомление при изменении (например, "конфигурация обновлена"), а handler выполняет действие (перезапуск nginx) только если уведомление было получено. Если жёстко прописать `restart` в tasks, nginx будет перезапускаться при каждом запуске playbook, даже если ничего не изменилось — это приводит к ненужным простоям сервиса и нарушает идемпотентность. Handler срабатывает только при реальных изменениях.

### 3. Как бы вы изменили плейбук, если бы нод было 50, а не 2?

Для масштабирования на 50 нод:
1. **Группировка в inventory** — использовать паттерны имён (`node[1:50]`) и группировать по ролям
2. **Параллельное выполнение** — флаг `--forks 10` для одновременной работы на 10 нодах
3. **Вынос переменных** — использовать `group_vars/` и `host_vars/` для разных конфигураций
4. **Тегирование задач** — добавить теги для выборочного запуска (`--tags install`)
5. **Проверка перед применением** — использовать `--check` (dry-run) и `--diff`
6. **CI/CD интеграция** — автоматический запуск через GitHub Actions при изменении кода


# Отчет по лабораторной работе №2

## Тема: Развертывание системы мониторинга инфраструктуры (Prometheus + Grafana)

## Цель работы
Развернуть полноценную систему мониторинга на базе стека Prometheus и Grafana для сбора и визуализации метрик с нескольких узлов инфраструктуры с использованием Ansible.

## Выполненные задачи
1. Развернут `prometheus-node-exporter` на всех узлах (`node1`, `node2`, `mon`) для сбора системных метрик.
2. Установлен и настроен сервер `Prometheus` на узле `mon` для сбора и хранения метрик.
3. Установлена и настроена система визуализации `Grafana` на узле `mon`.
4. Настроен Data Source в Grafana для подключения к локальному серверу Prometheus.
5. Импортирован стандартный дашборд **Node Exporter Full** (ID: `1860`) для визуализации метрик.

## Решенные проблемы
**Проблема:** Служба `prometheus-node-exporter` на узлах не запускалась, в логах была ошибка `listen tcp :9100: bind: address already in use`.  
**Причина:** Порт 9100 был занят rogue-процессом `/bin/node_exporter`, который запускался из Docker-контейнера.  
**Решение:** 
- Остановлен и удален конфликтующий Docker-контейнер: `docker stop node_exporter && docker rm node_exporter`.
- Запущена штатная systemd-служба: `systemctl start prometheus-node-exporter`.
