## Ход работы

Развернут контроллер ArgoCD в кластере K3s, настроена интеграция с GitHub-репозиторием манифестов (Pull-модель). Приложение `gitops-app` (nginx, NodePort 32011) развернуто через `Application` и синхронизировано. Включены политики `automated`, `auto-prune`, `self-heal`. Продемонстрированы: (1) Self-Healing — ручное `kubectl scale` до 5 реплик было автоматически откачено к 2 из Git; (2) Continuous Delivery — изменение `replicas: 3` через коммит в Git применилось в кластер без ручного вмешательства; (3) Rollback — возврат к ревизии 1 через `argocd app rollback`.

## Ответы на контрольные вопросы

### 1. GitOps vs CI/CD: Push-модель против Pull-модели
В ЛР10 использовалась **Push-модель**: GitLab CI сам выполнял `kubectl apply`, то есть внешний CI-системе выдавался `kubeconfig` с правами на запись в кластер. В **Pull-модели** ArgoCD работает как агент *внутри* кластера: он сам опрашивает Git, сравнивает желаемое состояние с фактическим и применяет разницу. Преимущества Pull-модели для безопасности: (а) секреты доступа к кластеру не покидают его периметр — CI не хранит kubeconfig и не может быть вектором компрометации кластера; (б) кластер не открывает исходящие соединения в CI (меньшая поверхность атаки); (в) любое изменение проходит через PR/коммит в Git, что даёт единый аудит-лог и контроль версий конфигурации; (г) CI-пайплайн может падать/меняться, но состояние кластера определяется только Git.

### 2. Single Source of Truth и антипаттерн `kubectl edit`/`scale`
Git объявлен единственным источником истины, поэтому любое ручное изменение ресурса (`kubectl edit`, `kubectl scale`, `kubectl apply` из другой копии манифеста) создаёт **дрейф**: фактическое состояние кластера перестаёт совпадать с задекларированным в Git. Это антипаттерн, потому что: (1) изменение нигде не зафиксировано — нет истории, автора, причины и возможности отката через Git; (2) при включённом self-healing ArgoCD молча затрёт ручную правку, что создаёт ложное ощущение «сломанного» администрирования; (3) при восстановлении кластера из Git ручное изменение будет потеряно. Правильный путь — изменить манифест, закоммитить и дождаться синхронизации.

### 3. Self-Healing: пошаговый сценарий удаления Pod
(1) Администратор выполняет `kubectl delete pod <pod>`. (2) `argocd-application-controller` через watch-механизм Kubernetes фиксирует изменение фактического состояния (количество живых подов ≠ ожидаемому). (3) **Reconciliation Loop** — периодический цикл сверки: контроллер берёт *желаемое* состояние из Git (реплика `main`, путь манифестов) и *текущее* из API-сервера кластера, вычисляет diff. (4) Статус приложения меняется на `OutOfSync`/`Degraded`, фиксируется дрейф. (5) При `self-heal: true` контроллер сам инициирует синхронизацию: `Deployment` получает указание создать недостающий под, ReplicaSet восстанавливает реплику. (6) Статус возвращается в `Synced`/`Healthy`. Роль Reconciliation Loop именно в том, что он непрерывно приводит реальность к декларированной модели, а не реагирует на события однократно.

### 4. Безопасность доступов: Deploy Key / Read-Only Token против личной учётки
Личная учётная запись разработчика обычно имеет права на *запись* в репозиторий. Если токен утечёт (через логи, образ, компрометацию ArgoCD), злоумышленник сможет пушить изменённые манифесты, и ArgoCD добросовестно развернёт вредоносную конфигурацию в кластер — GitOps превращается в вектор атаки. Кроме того, привязка к человеку нарушает принцип наименьших привилегий и создаёт проблему ротации (увольнение — остановка пайплайна). Deploy Key с флагом read-only или read-only Personal Access Token дают ArgoCD **только чтение**: система не может вносить изменения в Git, а в случае компрометации токена злоумышленник получит лишь доступ на чтение публичных манифестов, без возможности подмены. Токен изолирован от людей и ротируется независимо.

### 5. Архитектура ArgoCD: три ключевых компонента
- **`argocd-server`** — API-шлюз и веб-интерфейс: аутентификация/авторизация пользователей, отдача состояния приложений по gRPC/HTTP, приём CLI-команд (`argocd app sync` и т.п.).
- **`argocd-repo-server`** — сервис работы с Git: клонирует репозитории, рендерит манифесты (поддерживает plain YAML, Helm, Kustomize), кэширует результаты, чтобы не тянуть репозиторий на каждую сверку.
- **`argocd-application-controller`** — ядро GitOps: следит за Git и за кластером, выполняет Reconciliation Loop, вычисляет diff между desired и live состоянием, применяет синхронизацию, реализует auto-sync, auto-prune и self-heal.

Именно разделение на эти компоненты позволяет UI (server) и рендеринг (repo-server) не блокироваться долгими операциями применения (controller), а controller масштабируется по числу приложений.

## Выводы
GitOps-подход переносит ответственность за состояние кластера в Git: инфраструктура становится проверяемой, версионируемой и самовосстанавливающейся. ArgoCD корректно реализует Pull-модель, а политики `automated`/`self-heal`/`auto-prune` обеспечивают непрерывную доставку без ручных `kubectl apply`.
